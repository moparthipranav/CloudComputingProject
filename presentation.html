01 / OUR PROGRESSION
Our Journey: From Simple Greedy to the Winning Hybrid
How our tests showed why Greedy and Simulated Annealing needed each other to achieve the best result.
STEP 1: GREEDY APPROACH
Fast, But Overloads Servers

How it works: Puts talking VMs on the same server right away.

  • Good: Keeps communicating VMs close together.
  • Big Flaw: Makes permanent choices and gets stuck easily.
  • Dangerous Overload: Crammed VMs into just 116 servers, pushing CPU to 99.8% while leaving 12 servers empty!
STEP 2: SIMULATED ANNEALING
Balances Load, But Splits VMs

How it works: Makes smart random moves to spread the workload.

  • Good: Completely fixed server overload; balanced load by 94%.
  • Big Flaw: Tried so hard to balance load that it split up talking VMs across the datacenter.
  • High Traffic: Network traffic jumped by +37.5% because VMs were too far apart.
STEP 3: THE HYBRID SOLUTION
The Best of Both Worlds

How it works: Uses Greedy to group talking VMs first, then uses Annealing to fine-tune placements.

  • 24.6% Less Network Traffic than Greedy alone.
  • 30.5% Lower Network Delay (faster responses).
  • Keeps Server CPU Safely at 92.1% across all 128 servers!
02 / PROBLEM SETUP
The Goal: Where Should Each Virtual Machine Go?
We need to place VMs that talk frequently close together without overloading any physical server.
WHAT WE ARE OPTIMIZING (IN PLAIN ENGLISH)

Total Cost = Network Traffic + Network Delay + Server Imbalance

  • Network Traffic Cost: How much data travels across network cables. Placing talking VMs on the same server makes this zero.
  • Network Latency (Delay): The physical time taken for messages to travel between switches. Fewer hops means faster response times.
  • Server Load Balance: Making sure work is distributed fairly so no single server gets overwhelmed.
  • Strict Safety Rule: A physical server can NEVER exceed its maximum CPU, RAM, or network capacity. Zero violations allowed.
DATACENTER NETWORK LAYOUT (FAT-TREE)

128 Physical Servers connected by 80 Switches:

  • Inside the Same Rack: Super fast (0.02 ms, only 2 hops)
  • Inside the Same Pod: Fast (0.05 ms, 4 hops)
  • Across Datacenter: Slower (0.10 ms, 6 hops through core switches)
03 / APPROACH 1: THE GREEDY METHOD
The Greedy Algorithm: Fast and Dense, But Cooks Servers
How the simple greedy heuristic places VMs quickly, but leaves servers dangerously full.
HOW GREEDY WORKS & WHY IT FAILS
The Irreversible Choice Trap
  • The Simple Logic: Finds pairs of VMs that talk the most, and puts them on the first server that has enough free space.
  • Super Fast Execution: Runs in just 0.05 seconds for 1,000 VMs.
  • The 'Greedy Trap': Once a VM is placed, it can never be moved. When early servers fill up, later VMs that need to talk are forced far apart across the datacenter.
  • Dangerous Host Overload: Greedy stuffed 1,000 VMs into just 116 servers, pushing active servers to 99.84% CPU while leaving 12 servers completely empty!
  • Why Real Clouds Hate This: Running servers at 99.8% means servers overheat, slow down, and crash if a sudden burst of user traffic arrives.

04 / APPROACH 2: SIMULATED ANNEALING
Simulated Annealing: Great Load Balance, But Scatters VMs
How smart random moves balance server workloads, but unintentionally increase network traffic.
HOW ANNEALING WORKS & ITS TRADEOFF
Balancing Load vs Splitting VMs
  • Smart Exploration: Inspired by how hot metals cool slowly. It tests moving a VM to another server. It always keeps improvements, but sometimes accepts worse moves to avoid getting stuck.
  • Lightning-Fast Math: Only checks the moved VM and its neighbors instead of the whole datacenter (>60,000 checks per second).
  • The Good News: It successfully fixed server overload! Server load imbalance dropped by 94%.
  • The New Problem: Because it tried so hard to balance load across every server, it moved talking VMs apart to fill empty servers.
  • Traffic Jumped by +37.5%: Splitting up talking VMs across the datacenter caused network traffic to jump from 3.17e+05 up to 4.51e+05.

05 / APPROACH 3: THE HYBRID SOLUTION
Why Not Both? Start with Greedy, Fine-Tune with Annealing
Combining Greedy's tight clustering with Annealing's smart tuning beats both methods.
STEP 1: GREEDY STARTS
Builds Initial Clusters
  • Groups Heavy Communicators: Quickly places VMs that talk frequently together on nearby servers.
  • Fast Starting Baseline: Gives us a smart starting point so we never have to start from scratch.
  • Maximizes Local Traffic: Keeps as much communication as possible inside the same physical server.
STEP 2: ANNEALING REFINES
Fixes Overload & Traps
  • Untangles Mistakes: Moves stranded VMs so they share the same Top-of-Rack switch instead of core switches.
  • Safe Server Headroom: Gently moves VMs off 99.8% full servers onto nearby servers with open room.
  • Keeps Clusters Intact: Moves VMs within the same rack so talking pairs stay close.
THE WINNING OUTCOME
Best on Every Metric
  • 24.6% Lower Network Traffic than Greedy alone.
  • 30.5% Lower Network Delay (faster packet delivery).
  • 55.8% Better Server Balance across all 128 servers.
  • Keeps CPU safely at 92.1% (leaving healthy safety headroom).

07 / NETWORK PERFORMANCE
Faster Packet Delivery & Unclogged Network Cables
How keeping VMs in the same rack cuts delay and prevents network traffic jams.
WHY NETWORK POSITION MATTERS
  • Inside the Same Rack is Fast: Talking inside the same rack takes only 0.02 ms (2 hops). Sending packets across core switches takes 0.24 ms (12 times slower!).
  • Untangling Connections: Greedy left some talking VMs on opposite sides of the datacenter. The Hybrid swaps them so they share the same local switch.
  • 30.5% Faster Delivery: Average packet travel time dropped from 0.036 ms under Greedy down to 0.025 ms under Hybrid.
  • Less Cable Congestion: Peak traffic on main network cables dropped from 56% down to 41%, preventing dropped packets and slowdowns.
  • Fewer Hops Overall: Total network hops dropped to 9,238 (-67% compared to random placement).

08 / SERVER HEALTH
Keeping Physical Servers Safe, Cool & Reliable
Why running servers at 99.8% is dangerous and how the Hybrid fixes it.
HARDWARE HEALTH & SAFETY HEADROOM
  • The Need for Breathing Room: Real cloud systems need 8% to 10% free capacity on physical servers to handle sudden user traffic spikes without crashing.
  • Greedy's Severe Flaw: Running servers at 99.84% CPU means a single traffic burst will crash or slow down customer applications.
  • All 128 Servers Working: Greedy left 12 servers completely empty (0% load). The Hybrid activates all 128 servers smoothly.
  • Safe Peak Load (92.09%): Capped the busiest server at 92.09% CPU, ensuring healthy hardware without spreading talking VMs too far apart.
  • Zero Rule Violations: Never exceeds server RAM, CPU, or network limits across all 1,000 VMs.
